# Google Cloud, Azure and AWS: compare the same enterprise service

The useful question is which implementation can improve a defined business process at an acceptable total cost. A runtime feature list cannot establish that result. Compare the complete service: interpretation, enterprise evidence, business execution, user experience and operations.

**Research snapshot: 2026-10-09 UTC.** This chapter combines current official documentation with explicitly proposed architecture choices. No cloud deployment or comparative performance test was performed. Capabilities vary by feature, region, API version and commercial terms.

## Establish equivalent comparison boundaries

For custom code, compare **Google Agent Runtime**, **Microsoft Foundry hosted agents** and **Amazon Bedrock AgentCore Runtime**. These occupy the managed agent-hosting layer. A workplace assistant subscription, model endpoint and agent runtime are different purchases and responsibilities.

Google's current documentation places Agent Runtime within **Gemini Enterprise Agent Platform**; older material uses Agent Engine, and the API retains the `reasoningEngines` resource path. Microsoft documents **Microsoft Foundry** as the successor name to Azure AI Foundry and distinguishes prompt agents from hosted code. AWS documents **Amazon Bedrock AgentCore** as a set of capabilities, with Runtime providing hosting. [Google runtime](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/runtime), [Google deployment resource path](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/deploy-an-agent), [Microsoft naming and resource evolution](https://learn.microsoft.com/en-us/azure/foundry/what-is-foundry), [AWS AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)

Declarative agents remain legitimate alternatives when they meet the process requirements. Evaluate them as a separate service-design option; do not credit their managed orchestration to a custom-runtime comparison while omitting its restrictions or costs.

## Use one workload and one definition of success

The proposed benchmark is **service-disruption resolution**. A user reports a delayed delivery. The service authenticates the requester, retrieves current order state, finds the applicable policy, proposes a remedy, obtains approval when required, commits through a domain API and communicates the verified result. Some requests need clarification; some require human handling. All records and documents in the trial are synthetic.

Hold these inputs constant: case distribution, document corpus and permissions, tool schemas, policy thresholds, simulated reviewer response times, downstream latency and failures, concurrency, observation window and outcome rubric. Use the same domain API for transactional state across candidates. Do not compare a cached answer in one system with a live transaction in another.

| Acceptance dimension | Common evidence |
| --- | --- |
| Business value | Correctly resolved eligible cases, rework, elapsed resolution time and human minutes per eligible case |
| Grounding | Correct policy version, source citation, fresh order state and denied access to another user's records |
| Execution | Required approval, one committed remedy under duplicate requests, aggregate limits and timeout reconciliation |
| Experience | Clear clarification, understandable escalation, accessibility and accurate completion or pending status |
| Operations | Cold and warm latency, sustained concurrency, failure recovery, revocation, incident diagnosis and total service cost |

Agree thresholds before running trials. Publish counts and uncertainty, including failed and unresolved cases. Do not substitute model-graded answer quality for a business-system receipt.

Run two experiments. In the **controlled implementation trial**, hold the model/version and generation settings constant where supported, and record differences in wrappers, routing and retrieval. If equivalent access is unavailable, report the confounder. In the **native service trial**, let each team optimize its model and managed services against the same acceptance criteria. The latter compares deployable solutions; it does not isolate the runtime's contribution. Model retirement and regional availability must be checked before either trial.

## Differences that change implementation decisions

**MCP consumption, tool distribution, and server hosting are different capabilities.** Google documents Cloud Run hosting for remote MCP servers. Foundry can connect an agent to a remote MCP endpoint using a project connection; its Toolbox adds a managed distribution surface. AgentCore Runtime can host the MCP server application itself, while AgentCore Gateway exposes and mediates tool targets. Compare the business adapter, its hosting, and its consumers separately. [Cloud Run hosting](https://docs.cloud.google.com/run/docs/host-mcp-servers), [Foundry MCP authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication), [AgentCore MCP hosting](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-mcp.html)

AWS documents both stateless and stateful Streamable HTTP servers. Its protocol contract also distinguishes older session-based interactions from MCP 2026-07-28 multi-round-trip requests. Runtime affinity headers and application state must be assessed against the chosen SDK and protocol revision; a provider's session terminology is not a universal MCP requirement. [AgentCore MCP protocol contract](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-mcp-protocol-contract.html)

**Approval behavior depends on the integration path.** Foundry's direct MCP integration documents approval requests and continuation. For a custom hosted agent consuming Toolbox, Microsoft explicitly says the Toolbox endpoint does not block `tools/call` on the basis of `require_approval` metadata: the agent runtime must implement the pause, decision, and exact-call continuation. In the comparison trial, demonstrate this behavior and retain downstream business authorization; a metadata flag or system prompt is insufficient. [Direct MCP approval flow](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication), [Hosted-agent Toolbox approvals](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/use-toolbox-hosted-agent)

**Workflow durability is distinct from conversation persistence.** A session that resumes its files does not by itself reconcile an order remedy committed before a connection failed. Use the deterministic workflow layer for persisted business state, deadlines and recovery, while the agent performs interpretation within bounded steps. Foundry explicitly distinguishes background processing from resilience after process interruption; Step Functions also distinguishes execution models and explicit retries. Neither removes the need to protect downstream effects with idempotency. [Hosted execution](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents), [Step Functions semantics](https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html)

**Rollout mechanics are materially different.** A requirement for percentage canaries needs an accepted preview decision on the documented Google path. The documented Foundry endpoint requires a different rollout arrangement, such as separately addressed deployments with application-controlled routing, if the organization needs concurrent versions. On AWS, use a deliberately promoted named endpoint rather than allowing `DEFAULT` to become production implicitly. These are design implications of the versioning sources above, not tested rollout recipes. Include sessions already in progress, schema compatibility and state migration in rollback tests.

**Private ingress does not establish private egress or tenant authorization.** Trace the user-to-host, host-to-model, host-to-tool and tool-to-data paths independently. Runtime session isolation does not establish row-level access in a shared database. Google's access and gateway pages currently differ on VPC Service Controls wording; confirm the actual connectivity mode and support before making a perimeter commitment. [Access guidance](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/manage-agent-access), [gateway connectivity](https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/gateways/agent-gateway-overview)

**Telemetry and evaluation are workload dependencies.** Budget instrumentation, trace retention and reviewer calibration. For the controlled trial, export a common minimal event contract and use the same independently defined rubric. Native evaluator scores are not directly comparable when judges, prompts or supported tools differ. Use them to diagnose each implementation, with transaction checks providing a shared outcome anchor.

## Make regional feasibility a complete-path decision

Maintain a deployment bill of materials: runtime mode, model/version and endpoint, retrieval/index service, gateway, identity/delegation, evaluator, telemetry store, workflow engine and user channel. For every item record region, launch stage, quota, support terms, data storage, processing location and recovery dependency.

Google's location guide distinguishes infrastructure data-at-rest residency from model-processing location and lists feature exceptions. Foundry IQ availability differs by API version and portal path. AWS publishes a per-capability regional matrix; its evaluation documentation states that inference can cross regions even when data stays stored in the originating region. These are reasons to validate the full path rather than treat the runtime region as the entire data boundary. [Google locations](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/agent-locations), [Foundry IQ availability](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/what-is-foundry-iq), [AgentCore regions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html), [evaluation processing](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations-cross-region-inference.html)

Published autoscaling is not proof that the assembled service meets its recovery or latency target. Test throttling, dependency failure, credential revocation, deployment rollback and restoration. Establish the supported configuration and applicable service commitments before accepting production scope. This research makes no end-to-end availability claim.

## Apply the comparison across Day 0, Day 1 and Day 2

| Stage | Process and people decision | Technical comparison |
| --- | --- | --- |
| Day 0: redesign | Decide which handoffs disappear, which decisions remain with staff and who owns exceptions. Establish the manual and conventional-automation baselines. | Select candidate service compositions only after data, channel, action and recovery requirements are clear. |
| Day 1: build and launch | Train reviewers, staff the exception queue and observe whether users can complete the redesigned journey. | Run both trial types, validate integration and failure paths, rehearse promotion and release a restricted cohort. |
| Day 2: operate and improve | Measure resolution quality, rework, reviewer effort and whether released capacity was actually redeployed. | Monitor the complete dependency chain, improve bottlenecks, reassess model changes and repeat an exit exercise. |

Measure cost per **verified business outcome**, including failed attempts, model calls, retrieval, gateways, workflow execution, telemetry, support and human handling. Record one-time integration/migration costs separately. Platform choice changes this cost structure; token price alone cannot describe it.

## Choose for a specific advantage, then test the tradeoff

The following are architectural inferences from the documented composition, not rankings:

- **Google Cloud:** a credible candidate when existing analytical data and engineering practices make ADK, BigQuery and the Agent Platform operationally coherent. Test the benefit of that integration against regional intersections, SDK migration effort and dependence on preview rollout or identity features. See the [detailed GCP architecture](gcp-enterprise-architecture.md).
- **Azure:** a credible candidate when the redesigned process reaches users through Teams/Microsoft 365 and can use Entra delegation and Foundry's tool distribution. Test actual channel entitlements, permission-aware retrieval and deployment requirements. Distinguish the new Foundry resource/API path from classic projects rather than assuming old examples apply.
- **AWS:** a credible candidate when the process already uses event-driven services and domain APIs, and the team benefits from choosing AgentCore hosting plus explicit workflow, network and telemetry components. Compare the engineering cost of that composition and custom experience against its control and integration fit; verify the selected compute mode's regional coverage.

Finally, align **people, technology and operating philosophy**. Name who accepts outcomes and resolves exceptions; prove the integration and recovery path; decide how much ambiguity the organization permits the agent to resolve. Governance then sustains the redesigned service through accountable authority, evidence and change decisions. Use the [platform decision framework](platform-decision-framework.md) to record that choice and the [source notes](../research/cross-cloud-source-notes.md) to refresh the factual assumptions.
